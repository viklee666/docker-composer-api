## 1. 背景：这是什么问题

### 1.1 用户报告

在 durable 模式下并发使用时，**多个会话的记忆/工作内容互相串**：会话 A 的内容出现在会话 B 的回答里。
后续排查中又暴露出三个伴随症状：

- 子代理（Cursor Task 工具）不可用，模型说「没有提供 Task 工具」；
- 模型对同一个问题**回答两次**；
- 上下文瞬间膨胀到 1M+ 触发压缩（模型窗口设的是 200k）。

### 1.2 链路（关键：三跳）

```
Cursor IDE
  → cursor-byok（本地 Rust 网关，开源：github.com/leookun/cursor-byok，anthropic provider）
  → CPA / CLIProxyAPI（E:\MyCPA\CLIProxyAPI，claude messages 链路，本网关是它的 claude-api-key 上游）
  → 本网关（E:\docker-composer-api，/v1/messages，durable 模式）
  → Cursor SDK 上游（@cursor/sdk Agent）
```

### 1.3 本网关的 durable 机制（排查必备前置）

- **会话身份瀑布**（`src/durable-id.ts` 的 `durableIdentity`）：
  L1 显式会话头（11 个）→ L2 body 字段（session_id / metadata.user_id / prompt_cache_key …）
  → Responses 继承 seed → L3 `conversationSeed`（按请求内容推导）→ stickyKey。
- **Hub 键** = `durableAgentId(ownerHash \0 identity \0 model)` → 一个 SessionHub 槽 → 一个上游 SDK agent。
  **同身份 = 同 agent**，这是缓存命中的来源，也是串会话的载体。
- **身份来源归档**（`src/server.ts` 的 `noteDurableIdentity`）：产出 `identitySource`
  = `header` / `body-field` / `derived-L3` / `none`，进 `/health` 统计与 debug 快照。
- **硬约束**：durable / reuse（park + 复用 agent）**不许删、不许绕过**。所有修复都只能在其上加护栏与回退。

## 2. 诊断弯路（三次错判，务必读）

排查过程中我给出过三个错误判断，都被证据推翻。记下来是为了让你别重走：

### 弯路 1：以为是 byok 完全不带会话标识 → 内容推导碰撞

**当时的推理**：byok 的 anthropic provider 只发 `model/system/messages/max_tokens/stream/tools`，
不带 metadata、不带 session 头 → 网关只能走 L3 内容推导 → 同仓库同模板 prompt 会撞。
据此做了第一批护栏（`75264b9`），全部门控在 `identitySource === "derived-L3"`。

**为什么错**：用户实测「修了还串」。debug 快照显示这条链路的 `identitySource` 是 **`header`** 不是
derived-L3——护栏**零触发**。

### 弯路 2：以为是 CPA 把 byok「误判成原生 Claude Code」后才补 session 头

**被 Cursor 的独立审查推翻**：CPA 在 `claude-api-key` 链路上，对**任何**没自带 session 头的客户端
都会盖 `X-Claude-Code-Session-Id = CachedSessionIDRequired(apiKey)`（**每把 key 一个常量 UUID**），
**不依赖**原生客户端检测。而且快照里的指纹（`claude-cli/2.1.63` + `x-stainless-package-version: 0.74.0`
+ `OS: Linux`，而本机是 Windows）对应的是**服务器上旧版 CPA 的注入值**，不是 byok 桌面版的预设
（那是 `2.1.177`、无 `x-app`）。

### 弯路 3（最危险）：交叉验证规则里放行了 legacy user_id

方案 v1 写的是「legacy 格式 user_id 只要尾部 session 与头一致就采信头」。
**Cursor 审查指出这会重新打开洞**：新版 CPA 的 `injectFakeUserID`（`cache-user-id=false`）
恰好会生成 **session 段 = per-key 头值**的 legacy user_id——一旦 CPA 升级，头和 body 就「对上了」，
降权失效，串会话原样回来。

**最终规则（v2，已实现）**：**只有 JSON 形态的 `user_id.session_id` 与头逐字相等才采信；
legacy 一律不信**（包括碰巧一致的）。

## 4. 五个提交逐项说明

### 4.1 `75264b9` — derived-L3 防串扰护栏（第一批，方向对但当时没生效）

三个护栏，**全部只对 `identitySource === "derived-L3"` 生效**（显式 id 会话不可能碰撞，
且护栏会误伤只发增量的合法客户端）：

1. **新鲜会话护栏**（`session-hub.ts: inboundFreshSessionOnDeliveredSlot`）：
   入站 transcript 零 assistant 轮（digest 缺号）+ 槽已交付过输出 → 判定外来会话，
   本轮 stateless，槽不动。Responses 协议豁免（其 input 恒缺 assistant 文本）。
2. **tool_results 零交集护栏**（`cursor-runner.ts: toolResultsForeignToSlot`）：
   本轮全部工具结果 id（两侧剥 `call_` 前缀后比对）与槽的 issued/pending **零交集** → 外来结果。
   **检查放在 `resolvePending`/`abortHungDurableRun` 之前**——外来结果绝不能 cancel 对方
   正在等待的挂起 execute（这是原先破坏性最重的路径）。
3. **严格模式开关** `DURABLE_REQUIRE_EXPLICIT_ID`（默认关）：开启时 derived-L3 身份完全不进 Hub。
   这是**立即止血手段**：无 id 客户端零串扰，代价是零缓存。

另加 seed 指纹日志：derived-L3 命中时打 `[durable-identity] source=derived-L3 seed=<前12位>`。

### 4.2 `deabddd` — session 头降权（主问题的真正修复）

**判据**（`src/durable-id.ts`）：`claudeSessionHeaderTrusted(headers, body)`
— `x-claude-code-session-id` 仅当 body 的 `metadata.user_id` 是 **JSON 形态**
（对象或 JSON 字符串，真 claude-cli ≥2.1.78 的形态）**且其 session_id 与头逐字相等**时才采信。

**降权动作**：忽略该头（从 L1 候选剔除）+ 剥离 body 的 `metadata`（legacy 随机 user_id 若留在 L2
会给出每请求都变的身份，比串更糟）→ 身份落到 L3 → `identitySource` 归档为 `derived-L3`
→ **`75264b9` 的三个护栏就此激活**。

**关键实现点**：`durableIdentity`（管 seed）和 `noteDurableIdentity`（管 identitySource 归档）
**必须共用同一套降权函数**，否则会出现「seed 已是 L3、source 仍是 header」的劈叉，护栏依旧不生效。

**已知残余**（`plans/claude-session-header-demotion-plan.md` §2.5）：若中间层同时伪造
JSON user_id + 匹配的 per-key 头（新 CPA cloak 显式配置后的行为），交叉验证会通过。
**运维约束：不要在指向本网关的 CPA claude-api-key 条目上配 `cloak` / `fingerprint-profile`。**
未来硬化方向：device_id 跨请求稳定性校验（需跨请求状态，本期未做）。

### 4.3 `983be1f` — 拆宿主元工具过滤 + 已交付 tool_call 去重

**(a) 拆除 `HOST_META_TOOL_NAMES` 机制**（`tool-compat.ts` / `protocol.ts` / `prompt-delta.ts`）

`090d4a7` 当初为治「Claude Code 的 schema 对齐死循环」把 Task/GetMcpTools/CallMcpTool/
FetchMcpResource/SwitchMode/AskUserQuestion 等从**注册、历史渲染、工具结果提取**三处全部剔除。
**用户判定该循环的真根因是缓存错位，durable 上线后已消失**——过滤只剩副作用：byok 声明的 Task 被拦，
子代理整个不可用。现已全部拆除：客户端声明什么就注册什么、调用什么就转发什么、结果原样回流。
未声明的工具名仍被 `matchesClientTool` 自然拒绝（不需要名单）。
`isRitualAssistantText`（短仪式句抑制）保留——它只压制无实质产出的填充句。

**(b) 已交付 tool_call 去重**（`cursor-runner.ts: collectHeldToolCall`）

SDK 的消息级事件会**整段重放** run 的 assistant 内容（含早前轮次的 tool_use），
网关的 post-end 兜底提取会把已交付过的 tool_call 再发一次。护栏：id 在 `issuedToolCallIds`
且**不在 pending** → 丢弃并打 `[durable] dropped already-issued tool call`。
**仍在 pending 时必须放行重发**（SDK 可能对新调用复用同一 id），否则那个 execute 无人解决、挂到 TTL 拖死槽。

### 4.4 `c444ad0` — 碰撞分叉（collision fork）

**解决的问题**：护栏把输家会话拦下后，它**永远回不了 durable**——每轮工具结果对基础槽都是 foreign
→ 每轮全量 stateless → 每次都是全新 agent 重新评估任务 → 模型「再搜一次」停不下来。
实测 25 轮循环（快照 session `0e4e94c2`，消息数 5→47，直到客户端放弃）。

**机制**：用入站 transcript 里**最早的工具调用 id**（`lineageToolId`）派生专属分叉键。
这个标记同会话跨轮稳定（历史只追加）、跨会话随机不同（上游生成的 UUID）。

- `prompt-delta.ts: earliestLineageToolId` 提取（**只认调用侧 id**：tool_use / tool_calls /
  function_call；结果侧 id 不算证据）；
- 分叉槽不存在 → create + **全量 flatten 首程**（stateless 口径，但 agent 保留）；
- 分叉槽已存在 → 当普通 durable 会话续跑（增量 + path A/B）；
- **禁止递归分叉**（分叉内再触发护栏 → 退 stateless，否则同 marker 无限套娃）；
- 赢家的基础槽完全不受影响；
- 无 lineage（纯文本首轮碰撞、或压缩掉了调用侧 id）保持原 stateless 行为。

打点：`create:collision_fork` / `reuse:collision_fork` + `[durable] collision fork` 日志。

### 4.5 `7c3a4ee` — 分叉锁 + 仪式句正则修正

**(a) 分叉槽加锁（严重缺陷）**：`streamDurable` 持的是**基础键**的锁，分叉走**派生键**——
同一输家会话的并发请求会同时操作同一个分叉槽（破坏 Hub 互斥），且基础键的 finally 只收尾基础槽，
分叉槽永久卡在 `running`。修复：分叉自取其键的锁（`tool_results` 用 `acquire` 让挂起 execute 能等，
其余 `tryAcquire`；拿不到锁 → stateless + `fallback:fork_locked`），并在自己的 finally 收尾。
收尾逻辑抽成 `settleDurableSlotState`，两路共用。

**(b) 仪式句正则摘掉工具名**：`RITUAL_ASSISTANT_RE` 里还留着 `GetMcpTools`/`CallMcpTool`，
而这两个工具已可合法调用——模型只要在 ≤200 字的短回复里提到它们，整段被吞：
入站历史和**本轮上游输出**（`cursor-runner.ts` 的 waitedText 路径，直接导致空回复）两处都中招。

### Windows 环境坑（实测踩过）

- `python3` 是假桩，**要用 `python`**；
- heredoc 里嵌套引号容易断，复杂脚本**写临时 .py 文件**再跑；
- 源码是 CRLF，python 批量替换前先 `s.replace('\r\n', '\n')`，写回用 `newline=''`；
- 用 node 脚本分析快照时不要把脚本放在被遍历的目录里（会被 readdir 当成子目录）。

## 7. 给下一个接手者的建议

1. **不要动 durable/reuse 复用策略**——这是硬约束，所有问题都只能在其上加护栏与回退。
2. **护栏门控在 `identitySource === "derived-L3"` 是有意为之**：显式 id 的会话不可能碰撞，
   对它们施加护栏只会误伤只发增量的合法有状态客户端（第一批护栏就是这么写的，别去掉）。
3. **改身份逻辑时，`durableIdentity` 与 `noteDurableIdentity` 必须同步**（共用降权函数），
   否则 seed 与 identitySource 劈叉，护栏静默失效。
4. **护栏连串触发 = 有会话被锁死**，不是「护栏在努力工作」。看到同一 session 连续 N 次
   `foreign tool_results` 就要查是不是又出现了「永远回不去 durable」的路径。
5. byok 侧的问题（Task 工具集、缺 conversation_id、伪装头）见
   `plans/cursor-byok-client-issues.md`，**用户明确表示网关侧不修**，他会二开 byok。
6. 头降权的残余漏洞需要运维配合：**CPA 指向本网关的条目不要配 cloak / fingerprint-profile**。
